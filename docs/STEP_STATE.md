# 第五课：请求结束了，缓存为什么还不能还？

[返回首页](../README.md) · [第三课：同步批次](BATCHING.md) · [第四课：混合缓存](QWEN35.md) · [源码对应](SOURCE_MAP.md)

上一课里，请求结束后可以立即回收缓存，因为 Runner 返回前已经等设备算完。现在我们把这个等待拆开：CPU 先准备下一批，设备还在处理上一批。A 恰好在这时被取消，它占用的空间能直接交给 C 吗？

不能。取消表示后面不再需要 A 的回答，已经发给设备的操作仍可能继续读写 A 的空间。如果此时 C 写进来，两个请求就可能相互覆盖。

这一课用整数和手动事件把顺序摆出来。没有线程、模型或 NPU；你可以决定哪个事件先完成，看看什么时候才允许回收。真实生成仍走已有的同步引擎。

## 先跑一遍

在仓库目录执行，Python 3.10+ 即可，无需安装依赖或下载权重：

```bash
python -m minideepinfer.step_demo
```

开头会看到：

```text
1. [A, B] 还没算完，先取消 A。
   本次回收=()，空闲槽位=2/6
2. 准备 [B, C]：行号映射=(1, -1)
   A 占用=(0, 1)，B 占用=(2, 3)，C 占用=(4, 5)
   提前读取被拒绝：采样结果还没准备好。
```

总共 6 个槽位，A、B 各占 2 个。取消 A 后，它的槽位仍被保留，C 只能拿剩下的 `(4, 5)`。如果没有剩余空间，C 就得等，不能挪用 A 还在使用的空间。

这里的“下一批”只是已经准备好的成员和输入关系。结果未就绪时，B 还不能拿到本轮 decode 所需的 token；演示没有提前执行 B 的下一次模型计算。

## B 换了行，结果还是 B 的

上一批是 `[A, B]`，假设选出的 token 是 `[11, 21]`。下一批变成 `[B, C]`：

| 下一批的请求 | 在上一批的行号 | 这次输入从哪里来 |
| --- | --- | --- |
| B | 1 | 取上一批第 1 行的 token，也就是 21 |
| C | -1 | 新请求，取自己的输入 30 |

`-1` 是“上一批没有这个请求”的标记。B 虽然成了下一批的第 0 行，仍要取上一批的第 1 行；直接按新行号取旧输出，就会误拿 A 的 11。

[`batch_remap()`](../minideepinfer/step_state.py) 只按请求 ID 找行号，可以在结果就绪前计算。`StepState.inputs_for()` 才真正读取 token；它先查询 `ready` 事件，再按映射取值。

本例 C 的输入只有一个整数，方便看清行号。真实 prefill 往往有一整段 prompt，需要沿用第三课的 Step 和输入准备流程；这里没有实现这部分，也不处理未完成 prompt 块的 `None` 输出。

## “结果能读了”和“资源能还了”是两回事

继续看输出：

```text
3. 采样结果已就绪：B 接上 21，C 使用自己的新输入 30。
   本次回收=()，空闲槽位=0/6
4. CPU 已读完，但还有一次设备拷贝在用旧状态。
   本次回收=()，空闲槽位=0/6
5. 设备拷贝也完成了，现在才能归还 A 的槽位。
   本次回收=('A',)，空闲槽位=2/6
   新请求 D 复用了 A 的槽位：(0, 1)
```

这里特意设了两个事件。`ready` 表示采样结果已经可以读取；`last_use` 表示仍引用这份状态的设备操作也全部完成。例如，结果已经可供 CPU 使用，但另一项设备拷贝还没结束。演示用手动信号表示这种依赖，没有执行真实拷贝。

CPU 自己也要表态：调用 `close()`，表示已经读完，或者因为取消、异常而放弃这份结果。关闭以后再次读取会报错。关闭不等于强制结束设备操作；如果计算还没完成，资源继续保留。

`DeferredRelease` 做的事很简单：

- `retain(state)`：记住这份状态还在使用哪些请求的资源，要在发起计算前调用。
- `retire("A")`：A 已结束或取消，以后不要再给它发起新计算。
- `collect()`：检查哪些状态已经用完，再归还没有剩余使用者的已结束请求。

一份状态只有在 CPU 关闭读取、采样事件完成、最后一次设备使用也完成后，才算用完。即使这份状态用完了，另一个保留的状态还引用着 B，也不能释放 B。

本课有意按整批保留资源，便于逐行核对。因此 CPU 为了读 B 而保留上一批时，A 的资源也可能多等一会。这是一个容易检查的保守规则。要更早回收，需要为不同资源分别追踪使用者。

## 再看最后一次回收

程序在第五步之前保留了 `[B, C]` 的新状态。上一批退出后，B 仍被新状态保护。最后 B、C 结束，设备也完成，但 CPU 还没读出 `[22, 31]`，它们的槽位继续保留。

CPU 读完并关闭，下一次 `collect()` 才归还它们，最后得到：

```text
   读出下一轮 token：(22, 31)
   每个请求只释放一次：['A', 'D', 'B', 'C']；空闲槽位=6/6
```

D 在例子里没有发起计算，因此它结束后可以直接回收。A、B、C 都要等各自的使用者完成。同一个请求反复通知结束，也只会释放一次。

调用约定放在一起看更清楚：这些方法在同一个线程顺序执行；请求 ID 在本次运行中不重复；构造状态时固定请求顺序和 token，之后不修改；请求先通过 SlotPool 分配资源，再保留状态。清理回调应完成同步的主机清理且不抛异常，不能偷偷发起仍会访问旧槽位的设备工作。

如果设备异常后无法确认工作已结束，就不能把事件标成完成来强行回收。当前真实 Runner 的异常同步约定仍然有效；NPU 事件和设备故障处理留到下一步验证。

## 跟 DeepInfer 的哪部分对应？

参考版本固定为 `8b16149741a4935e1dec8cea27853f273b374c5b`：

| 原版入口 | 本课保留的意思 | 本课的简化 |
| --- | --- | --- |
| [`WorkerStepState`](https://github.com/deepseek-ai/DeepInfer/blob/8b16149741a4935e1dec8cea27853f273b374c5b/deepinfer/worker/zos_status.py#L8) | 一轮执行结束前后，仍有需要保留的状态和事件 | StepState 只有请求 ID、整数结果和两个完成信号 |
| 同文件的 `MetadataZOS.remap` | 当前第 i 行对应上一批第几行，新请求标为 -1 | 用 Python tuple 表达，没有设备张量、padding 或输入修正内核 |
| [`DeferredRelease`](https://github.com/deepseek-ai/DeepInfer/blob/8b16149741a4935e1dec8cea27853f273b374c5b/deepinfer/engine/llm_engine.py#L64) | 已经交给后续步骤使用的资源，不能过早归还 | 用整批状态保护逻辑槽位，显式查询完成条件 |

上游管理的对象包括 sequence metadata、输出池和状态/块的 pin 等，本课没有逐项实现。这里把逻辑槽位作为直观例子，并不表示原版总把整批 KV 多留一轮；`ready` / `last_use` 也是本课的接口设计，不是原版字段的直接复制。

本课完成的是状态和依赖实验。[第六课](NPU_EVENTS.md)进一步换成 Ascend 910C 的真实事件与微型张量，检查设备拷贝、读取和槽位复用。真实模型仍需独立检查同步与新路径的结果，两课均没有性能结论。

## 自己改两个地方

把 `step_demo.py` 中的 `last_use.complete()` 往后挪，观察 A 的槽位是否继续保留；再把 `previous.close()` 暂时去掉，即使两个设备事件都完成，A 也不会回收。这两处等待分别由设备和 CPU 引起。

测试还枚举了三个完成条件的全部 6 种到达顺序，检查前两个条件完成时始终无法复用槽位，最后一个完成后才能复用；另有批次重排、跨两份状态保护、取消、异常后放弃输出及重复释放检查：

```bash
python -m unittest discover -s tests -p test_step_state.py -v
```
